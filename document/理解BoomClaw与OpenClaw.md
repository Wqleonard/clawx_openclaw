# 理解 BoomClaw 与 OpenClaw（通俗版）

> 适合第一次接触本项目的同学：看完能知道「系统怎么跑起来」「AI 为什么能工作」「文件系统为什么能打通」。

---

## 1. 先用一句话理解这个项目

`BoomClaw = 桌面应用壳（Electron + React） + OpenClaw 运行时（Agent/Gateway/Skills）`

你可以把它想成：

- **BoomClaw**：你看得见、点得着的桌面界面（聊天页、设置页、文件树）
- **OpenClaw**：在后台真正执行 AI Agent 的“引擎”

---

## 2. OpenClaw 是什么？为什么需要它？

OpenClaw 不是一个聊天窗口，而是一个 **Agent Runtime（代理执行运行时）**。  
它负责：

- 维护会话（session）
- 调用模型（LLM）
- 执行工具（tools/skills）
- 管理渠道插件（如外部消息渠道）
- 输出事件流（流式 delta、tool use、final 等）

简单说：**OpenClaw 是“大脑+执行器”，BoomClaw 是“控制台+仪表盘”。**

---

## 3. 关键名词先看懂

- **Gateway**  
  OpenClaw 的后台服务入口。BoomClaw 通过它发请求、收事件。

- **Agent**  
  一个“带身份和策略”的 AI 实例。不同 Agent 可有不同配置/会话。

- **Skills**  
  给 Agent 的“能力包/插件包”。可理解为“可安装工具集合”。

- **Tool**  
  单个可调用能力，例如读文件、写文件、搜索等。

- **Prompt（System Prompt）**  
  给模型的行为说明书，决定它“怎么思考、怎么回答、什么时候调工具”。

- **IPC**  
  Electron 里前端和主进程通信的机制（Renderer 不能直接做很多系统操作）。

- **Preload**  
  安全桥层，把主进程允许的能力暴露给前端（`window.electron.*`）。

- **LLM（Large Language Model）**  
  真正“生成文字”的模型（例如 GPT、Claude、Qwen 等）。Agent 不是模型本身，而是“使用模型并调工具的执行体”。

- **Token**  
  模型处理文本的最小计费/计算单位。输入越长、输出越长，token 越多，耗时和成本越高。

- **上下文窗口（Context Window）**  
  模型一次能“看到”的总内容上限（系统提示词 + 历史消息 + 工具结果 + 你本轮输入）。

- **Tool Calling（工具调用）**  
  模型先产出“我要调用哪个工具、传什么参数”，再由运行时执行工具并把结果回传给模型继续推理。

---

## 4. 整体架构：谁和谁在说话

当前核心链路是：

1. **React Renderer（前端页面）** 发起操作（发消息、读文件等）
2. 通过 **Preload** 暴露的 API 走 **IPC**
3. 到 **Electron Main**（主进程）执行系统能力
4. 主进程再去调用 **Gateway（OpenClaw）**
5. Gateway 调模型/工具并把事件推回前端

可以理解为：

- 前端：负责展示和交互
- 主进程：负责系统权限、文件、进程管理
- Gateway：负责 AI agent 的真正执行

---

## 5. 本项目怎么“连上 OpenClaw”的？

### 5.1 是否要求用户手动安装 OpenClaw？

不要求。项目设计是 **应用内置 OpenClaw runtime**，应用启动时自动拉起 Gateway（默认开启）。

### 5.2 OpenClaw 数据放哪里？

当前统一使用用户目录下的 `~/.openclaw`（配置、skills、agents、sessions、context 等）。

这不代表用户要手动部署；这是应用运行时自动维护的数据目录。

---

## 6. AI 聊天是怎么工作的？

当你在聊天框发送一句话，流程大致是：

1. 前端把消息发给 Gateway（RPC）
2. Gateway 开始跑当前会话
3. 过程中可能产生：
   - 流式文本（delta）
   - 工具调用（tool_use）
   - 工具结果（tool_result）
4. 最后返回 final，前端落入历史

所以你看到“边生成边显示”“工具状态变化”，本质是 Gateway 在发实时事件。

### 6.1 从 LLM 角度看，一轮问答到底发生了什么？

可以拆成 6 步：

1. **组装输入上下文**  
   包含：system prompt、会话历史、你当前输入、可能的工具定义/上下文文件。
2. **发给 LLM**  
   模型先判断“直接回答”还是“先调工具”。
3. **如果要调工具**  
   模型输出 tool call（结构化参数），由 Gateway 执行。
4. **工具结果回注入**  
   Gateway 把 tool result 作为新上下文再喂给模型。
5. **模型继续生成**  
   可能经历多轮“思考 -> 调工具 -> 再思考”。
6. **输出 final**  
   前端收到完整结果并落历史。

### 6.2 为什么有时 AI 会“慢”？

常见原因：

- 上下文太长（token 多）
- 触发了多次工具调用
- 使用了更强但更慢的模型
- 网络/供应商延迟波动

---

## 7. Prompt / Agent / Skills / LLM 四者关系

更精确地说：

- **LLM**：负责生成“下一步文本/工具调用”
- **Prompt**：约束 LLM 的行为边界与风格
- **Skills/Tools**：提供“能做的动作”
- **Agent Runtime（OpenClaw）**：负责调度 LLM 与工具循环

所以一个稳定 Agent 不是“换个大模型”就够了，而是四者都要协同。

## 8. 文件系统是怎么打通的？

### 8.1 已经打通的部分（当前可用）

- 左侧文件树（打开目录、浏览、右键操作）
- 文件读写（新建、重命名、移动、复制、删除、保存）
- 文件监听（变化后刷新）
- 文件标签页（FileTabs）
- “添加到上下文”（把选中文件镜像到 agent context 目录，便于 AI 读取）

### 8.2 正在推进的部分

- 让 Agent 通过**标准工具链**直接写入你绑定的小说工作区（而不是仅靠手动导入编辑器）
- 会话级工作区绑定策略（session -> workspaceRoot）持续完善

---

## 9. 为什么要“会话绑定工作区”？

因为“你选了目录”这件事，默认只对文件树/编辑器生效。  
如果不绑定到 Agent 运行上下文，AI 不一定知道应该读写哪个目录。

推荐策略（本项目正在按这个方向收敛）：

- 每个会话绑定一个 `workspaceRoot`
- 工具读写只允许在该根目录内
- 使用相对路径（例如 `02_正文/第03章.md`）

这样最适合“连续写小说”场景：

- AI 读上文
- AI 续写新章
- AI 回头改前文
- 全程不会乱写到无关目录

---

## 10. 新手怎么用（小说场景）

建议按这个顺序：

1. 打开/确认小说工作目录
2. 准备基础文件：
   - `人物设定.md`
   - `世界观.md`
   - `总纲.md`
   - `第01章.md`
3. 把关键设定文件“添加到上下文”
4. 在聊天里下明确任务：
   - “基于总纲和人物设定，续写第02章，2000字”
5. 检查产出，保存到章节文件
6. 继续下一章，反复迭代

补充建议（能显著提升效果）：

- 在指令中明确体裁、字数、视角、节奏（减少模型自由发挥偏差）
- 把“长期设定”放进上下文文件，把“本章要求”放在当前消息
- 定期让 AI 先“总结已写内容”，再继续续写（降低上下文漂移）

## 11. 你可能会遇到的典型问题

- **看到“Workspace is not selected”**  
  含义：前端有目录状态，但主进程未同步。当前版本已在持续修复启动竞态并做自愈同步。

- **AI能读但不能直接写文件**  
  含义：标准工具执行链路尚在分步打通中，当前可先用“上下文 + 编辑器保存”闭环。

- **同样的指令每次结果不同**  
  含义：LLM 采样有随机性（温度、top-p 等参数会影响稳定性）。

- **回答突然“失忆”或遗漏设定**  
  含义：上下文窗口有限，早期信息可能被截断。可通过“设定文件 + 摘要回灌”缓解。

- **不确定文件应放哪里**  
  建议：小说主文件放用户可见工作目录（如 Documents），不要放 `~/.openclaw` 运行目录。

---

## 12. 一句话总结

BoomClaw 负责“好用”，OpenClaw 负责“能干活”；  
当 Agent（策略）+ Skills（能力）+ Workspace（边界）三者打通后，  
你就得到一个可以长期协作写小说的 AI 工作台。
