# StoryClaw 自动更新方案

> 目标：不依赖 GitHub Releases，只通过后端和对象存储完成桌面端自动更新（macOS + Windows，含 x64/arm64 架构）。

---

## 1. 背景与目标

当前项目已经具备 Electron 自动更新基础能力（`electron-updater` + `AppUpdater` + 设置页更新 UI）。  
本方案目标是在保留现有代码结构的前提下，把更新源从 GitHub 对齐到“自有后端 + OSS/CDN”。

核心要求：

1. 客户端继续使用 `electron-updater` 标准能力，不在 Renderer 侧自行下载和替换安装包。
2. 更新判断由主进程执行，Renderer 仅展示状态和触发动作。
3. 后端负责版本发布、元数据生成、渠道管理、灰度策略与下载鉴权。
4. 支持稳定版和预发布版渠道，并兼容 macOS/Windows 多架构。

---

## 2. 总体架构

更新链路建议如下：

1. **客户端（Main）** 在启动后调用 `checkForUpdates`。
2. `electron-updater` 从自有更新源读取 channel 对应的 yml 元数据。
3. 若存在新版本，客户端进入 `available`，由用户点击下载或自动下载。
4. 下载完成后触发 `downloaded`，客户端执行 `quitAndInstall`。
5. 应用重启后，版本生效并在 UI 展示新版本号。

职责边界：

- **Renderer（React）**：只做展示和交互（检查/下载/安装/开关）。
- **Main（Electron）**：唯一更新执行器（校验、下载、安装、事件转发）。
- **Backend + Storage**：唯一发布源（元数据、安装包、渠道、灰度、审计）。

---

## 3. 客户端方案（前端 + 主进程）

## 3.1 Renderer 侧要做什么

Renderer 保持“轻职责”：

1. 调用现有 IPC：
   - `update:check`
   - `update:download`
   - `update:install`
   - `update:setAutoDownload`
   - `update:status`
2. 监听事件：
   - `update:status-changed`
   - `update:auto-install-countdown`
3. 展示国际化文案（已存在 `settings.json` 的 `updates` 节）。
4. 暴露用户开关：
   - 自动检查更新
   - 自动下载更新

Renderer **不要**做的事：

- 不直接请求更新包 URL。
- 不自己比对 semver。
- 不处理平台/架构分流。
- 不直接调用第三方更新服务。

## 3.2 Main 侧要做什么

Main 使用 `electron/main/updater.ts` 的 `AppUpdater` 作为唯一更新入口，建议增强点：

1. **统一渠道语义**
   - 建议统一为：`latest | alpha | beta`
   - 当前设置中 `stable | beta | dev` 需映射到上述渠道，避免歧义。

2. **统一更新源**
   - 仅保留 `generic` 源到自有后端地址（或你的 OSS 入口）。
   - 不再依赖 GitHub provider。

3. **启动检查策略**
   - 由 `autoCheckUpdate` 控制首启后延迟检查（当前已实现）。
   - 检查失败回传明确错误，避免 UI 卡在 checking 状态（当前已处理）。

4. **下载安装策略**
   - `autoDownload` 与设置联动。
   - 下载完成后支持倒计时安装 + 用户取消（当前已实现）。

5. **运行信息上报（可选）**
   - 上报匿名设备信息用于灰度（平台、架构、当前版本、渠道、机器标识哈希）。

---

## 4. 后端方案（核心）

后端建议拆为两层：

1. **更新控制 API（业务层）**
2. **静态更新产物分发层（OSS/CDN）**

## 4.1 发布产物规范（必须）

每次发布后必须生成：

1. 安装包：
   - macOS: `dmg/zip`（x64、arm64）
   - Windows: `nsis exe`（x64、arm64）
2. 元数据：
   - `latest.yml`（Windows 主元数据）
   - `latest-mac.yml`（macOS 元数据）
   - 对预发布渠道对应 `alpha*.yml` / `beta*.yml`
3. blockmap（差分更新用）
4. sha512 与文件大小信息（由 electron-builder 生成并写入 yml）

目录建议：

```text
updates/
  latest/
    latest.yml
    latest-mac.yml
    StoryClaw-0.2.6-win-x64.exe
    StoryClaw-0.2.6-win-arm64.exe
    StoryClaw-0.2.6-mac-x64.zip
    StoryClaw-0.2.6-mac-arm64.zip
    *.blockmap
  alpha/
  beta/
  releases/
    v0.2.6/
      ...完整归档
```

## 4.2 更新 API（建议）

虽然 `electron-updater` 本身可直接读取 yml，但你们有自有后端，建议再提供“策略接口”：

1. `POST /desktop-updates/check`
   - 入参：`platform`, `arch`, `currentVersion`, `channel`, `osVersion`, `appVersion`, `machineIdHash`
   - 出参：`shouldUpdate`, `targetVersion`, `channel`, `rollout`, `reason`, `feedBaseUrl`

2. `GET /desktop-updates/changelog?from=0.2.5&to=0.2.6&lang=zh-CN`
   - 返回用于 UI 展示的更新说明（可选）。

3. `POST /desktop-updates/events`
   - 上报检查/下载/安装结果，用于发布质量监控（可选）。

说明：  
客户端最终下载仍应通过 yml + 安装包链接完成；策略 API 负责“是否推送、推给谁、何时推”。

## 4.3 平台与架构匹配规则（必须明确）

建议后端统一使用 Electron 标准值：

- `platform`：`darwin` / `win32`
- `arch`：`x64` / `arm64`

匹配逻辑：

1. 客户端上报 `platform + arch + currentVersion + channel`。
2. 后端先做版本门槛判断，再做渠道判断，再做灰度命中判断。
3. 命中后返回该渠道 feed 基地址（如 `https://updates.example.com/latest`）。
4. `electron-updater` 在该目录自动取对应 yml，再选具体安装包。

## 4.4 版本规则（建议）

统一 semver：

- 稳定版：`0.2.6`
- alpha：`0.2.7-alpha.1`
- beta：`0.2.7-beta.1`

约束：

1. 不允许发布回退版本覆盖同渠道。
2. 预发布仅在预发布渠道可见（除非手动放开）。
3. 允许“跳过版本”策略（如只推到某个最小版本以上）。

## 4.5 灰度策略（建议）

后端可按以下维度做灰度：

1. 平台：先 Windows 后 macOS（或反之）。
2. 架构：先 x64，再 arm64。
3. 百分比：`1% -> 10% -> 30% -> 100%`。
4. 白名单：内部账号、测试设备先行。

灰度建议落库字段：

- releaseId
- channel
- targetVersion
- platform
- arch
- rolloutPercent
- startAt/endAt
- paused

---

## 5. 安全与签名

自动更新必须满足签名与完整性要求：

1. **macOS**
   - 应用签名 + notarization 必须通过。
   - 安装包与 yml 哈希一致。

2. **Windows**
   - 建议代码签名（即使可关闭校验，也不建议长期关闭）。
   - 如果签名发生在打包之后，必须回写 yml 中 sha512。

3. **下载链路**
   - 全站 HTTPS。
   - 可加短期签名 URL（按需）。
   - OSS/CDN 缓存策略对 yml 建议 `no-cache`，对历史安装包可长期缓存。

---

## 6. 与当前仓库的对齐改造清单

## 6.1 客户端（代码）

1. `electron/main/updater.ts`
   - 统一 channel 映射（`stable/dev` -> `latest/alpha/beta` 之一）。
   - 固定 feed 到自有后端地址。

2. `src/stores/settings.ts` + `electron/utils/store.ts`
   - 对齐 `updateChannel` 的枚举和默认值。

3. `electron-builder.yml`
   - 仅保留你们需要的 publish provider（建议 generic）。

4. `src/components/settings/UpdateSettings.tsx` 和 `src/pages/Settings/index.tsx`
   - 保持现有 UI，补充渠道选择（如需要暴露给用户）。

## 6.2 后端（服务与发布）

1. 发布流水线产出 channel 化目录和 yml。
2. 提供可观测更新策略接口（可选但推荐）。
3. 建立发布记录、灰度记录、安装结果上报看板。
4. 明确“紧急回滚”机制：暂停某版本推送 + 恢复上一稳定版本。

---

## 7. 端到端时序（推荐）

1. CI 打包 `v0.2.6` 多平台多架构产物。
2. 签名/公证完成，校验 yml hash 一致。
3. 上传 `updates/latest/`，写入发布记录。
4. 客户端启动，读取本地设置（channel=latest，autoCheck=true）。
5. Main 调用更新检查，命中新版本。
6. Renderer 显示“可更新”，用户点击下载或自动下载。
7. 下载完成后安装重启。
8. 重启后上报安装成功事件。

---

## 8. 验收标准（建议）

1. 在 macOS x64/arm64、Windows x64/arm64 均能正确命中对应安装包。
2. 预发布版本不会污染稳定渠道用户。
3. 更新失败可回退到手动下载，不阻断应用启动。
4. 设置中的“自动检查/自动下载”开关真实生效。
5. 发布后 30 分钟内可看到检查成功率、下载成功率、安装成功率。

---

## 9. 一句话结论

本项目应继续以 `electron-updater` 为更新执行核心，Renderer 只做 UI；后端负责“版本策略 + 渠道灰度 + 元数据分发 + 安全签名”，通过自有更新源完整替代 GitHub 更新链路。
